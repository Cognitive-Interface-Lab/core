# Architecture

## Why a backbone

Trilix (Next.js app) and Orbit (local daily brief and voice assistant) need the same things: talking to any model provider, calling tools, recording what happened, and exposing it all safely to several front ends. Building each of these once, as a framework, lets every product be a thin client.

An assessment of the Trilix codebase on 2026-10-11 found good foundations (TypeScript strict with zero errors, CI, a server-only graph store with no React imports, eleven providers) but nothing reusable as a backbone yet:
- The provider layer is one `switch` with no common interface, keys live in browser `localStorage`, and model logic imports `@xyflow/react`.
- Branch, fork and merge are not engine operations. Provenance is a single JSON column, and there is no event log or replay.
- There is no package boundary or public API, and the tests are nine ad-hoc scripts.

## Modules

    contracts  ←  models, tools, graph  ←  credentials, runtime  ←  server  ←  clients, examples, apps (cli)
                                 graph  ←  graph-sqlite, graph-postgres  (apps pick one)

- **contracts:** zod schemas for messages, tools, tool calls, models, stream events, errors, and later graph events. The single source of every shape, exported as types and JSON Schema (which feeds the generated Python client).
- **models:** the `ModelProvider` interface (`capabilities`, `chat`, `stream`), `ProviderRegistry`, `CredentialStore` (memory and environment here; persistent stores live in `credentials`), `listModels` on providers, and `ModelRouter` (ordered fallback, per-attempt timeout, attempt log). Adapters are built on the Vercel AI SDK. One OpenAI-compatible adapter covers OpenAI, Ollama, OpenRouter, Groq, Cloudflare Workers AI, Vercel AI Gateway (M2d) and any OpenAI-compatible server whose address comes from the sign-in (the `openai-compatible` preset, flagged `requiresBaseURL`). An Anthropic adapter serves the Claude API and Claude Platform on AWS (M2e). A Google adapter serves Gemini, and an Azure OpenAI adapter serves Azure's v1 API with the deployment name as the model (M5a). They all share one AI SDK layer, and each preset names its adapter.
- **tools (M2):** tool registry, MCP client (use any MCP server), MCP host (offer our tools), and policy (which channel may call which tool; confirmation for side effects).
- **runtime (M2):** one turn or flow: messages → model → tool calls → events, with streaming, cancellation and budgets.
- **graph (M3):** branch, fork, merge and cross-reference as operations over an append-only event log, which gives provenance and replay. Graph state is a projection of the log. `ProcessGraph` is the one writer. Storage sits behind the `GraphStore` interface: `graph-sqlite` (Node's built-in SQLite) for local apps, `graph-postgres` (Drizzle) for Trilix, and an in-memory store for tests. One contract test suite (`@core/graph/testing`) runs against every store. The runtime records turns on a branch (`runBranchTurn`) and replays branches (`replayBranch`).
- **credentials (M2b):** where sign-ins are kept and how they are obtained. `SecretStore` (OS keychain, a `0600` fallback file, memory), `PersistentCredentialStore` (saved records to provider credentials, with OAuth renewal), `ChainCredentialStore` (environment first), and the terminal sign-in flows (PKCE plus a local callback receiver; OpenRouter and Cloudflare).
- **cli (M2b):** the `core` command: `login`, `logout`, `status`, `models`, `config`, `ask`, `chat`, and `completion` for Tab completion in bash (M2c). An app on top of `credentials` and `runtime`.
- **server (M4):** the HTTP API (providers, models, chat, turns over SSE, graph operations) as one web-standard handler, `createCoreHandler`, plus an OpenAPI document built from the contracts. The host app supplies who is asking, their credentials and graph access. Trilix mounts it in a Next.js route; `core serve` runs it on 127.0.0.1 behind the local bridge, for sites the user paired and programs on the machine. The MCP endpoint and server-side tools over HTTP follow (core#152).
- **clients (M4):** `@core/client`, a browser-safe TypeScript client written over the contracts, and a Python client generated from the OpenAPI document (core#153). Orbit's voice layer stays in Python and talks to the backbone through it.

## Decision log

- **Framework first** (owner, 2026-10-11). Build the backbone before porting Trilix (M5) and building Orbit on it (M6). Risk noted and accepted: a long stretch without product progress. Mitigation: every milestone ends with a runnable example.
- **TypeScript core; other languages via HTTP, MCP and generated clients** (owner, 2026-10-11). One implementation to maintain, shared with Trilix.
- **Standards over custom protocols** (lead, 2026-10-11). The AI SDK for provider wire formats, MCP for tools, OpenTelemetry for tracing, Drizzle for storage. The backbone owns only what makes Trilix different: the process graph, event log, provenance and replay. Rationale: a single maintainer cannot keep many hand-written adapters current.
- **TypeScript 5.9 for M1** (lead, 2026-10-11). TypeScript 7 (the native compiler) is out, but lint tooling support is unproven. Migration is a separate issue. *Superseded 2026-10-12, see below.*
- **The graph engine and event log come in M3, minimal but real** (lead, 2026-10-11). An event log is far harder to retrofit than to start with. M1 and M2 contracts leave room for graph events.
- **Cloud developer sessions push their own branches** (lead, 2026-10-11). A cloud container is discarded, so unpushed work is lost. This repo's developer reference allows pushing issue branches (never `main`, never force).
- **Workspace export condition is `@core/source`** (lead, 2026-10-11, core#12). A bare `source` condition collides with third-party packages that publish one (`eventsource-parser`), which made TypeScript type-check their raw sources. Vitest also needs it under `ssr.resolve.conditions` (core#14).
- **MCP through the official SDK's low-level `Server` and `Client`** (lead, 2026-10-11, M2). The low-level server takes our JSON Schemas as they are, with no second schema library. Tests connect client and host with the SDK's in-memory transport, so they never spawn processes or touch the network.
- **MCP tools are untrusted by default** (lead, 2026-10-11, M2). Imported MCP tools are allowed only on the `local` channel, and count as having side effects (so they need confirmation) unless the server marks them `readOnlyHint: true`. Stdio servers receive only the SDK's minimal default environment (HOME, LOGNAME, PATH, SHELL, TERM, USER, as `getDefaultEnvironment()` in SDK 1.32 returns it), never our API keys. TERM is accepted: it is not a secret (lead, 2026-10-12, core#38).
- **Tool arguments are validated by their owner** (lead, 2026-10-11, M2). Local tools are declared with zod through `defineTool`, which validates arguments. MCP servers validate their own. The registry has no JSON Schema validator in M2.
- **A turn runs tools one at a time** (lead, 2026-10-11, M2). A turn is rounds of model → tool calls → results until the model stops calling tools, or a budget (rounds, output tokens, wall time) ends it. The default limit is 8 rounds. Parallel tool calls wait until they are needed.
- **TypeScript 7 checks, TypeScript 6 serves the tools** (lead, 2026-10-12, core#23). The TypeScript 7 compiler (installed as the `typescript-7` alias) type-checks every package, about 4x faster than 5.9. TypeScript 7 ships no stable JavaScript API, and typescript-eslint supports TypeScript only up to 6.0, so the `typescript` package stays on 6.0 for typescript-eslint and tsdown. Both install a `tsc` binary, so `typecheck` scripts call TypeScript 7 by path, never a bare `tsc`. tsup is replaced by tsdown because tsup's type build fails on TypeScript 6 and later; the build output keeps the same file names and exports. TypeScript 6 stopped loading `@types/*` by default, so the base tsconfig lists `"types": ["node"]`. When typescript-eslint supports TypeScript 7, `typescript` moves to 7 and the alias goes.
- **Graph state is a projection of an append-only log** (lead, 2026-10-12, M3). A graph is its records `{ graphId, seq, at, event }`, with `seq` gapless from 1, and six event types: `graph-created`, `branch-created`, `message-added`, `turn-recorded`, `branches-merged`, `cross-referenced`. A node is one message. `turn-recorded` stores a turn's `TurnEvent`s exactly as the runtime emitted them, so the model, the route attempts, the tool results and the usage behind every answer stay in the log; the projection takes the turn's nodes from its `turn-finish` messages. The engine checks every event against the projection before appending it, and appends use optimistic concurrency (a stale `expectedSeq` fails with `conflict`).
- **Merges are recorded, not computed** (lead, 2026-10-12, M3). A merge node has two parents and a strategy: `append` (the target's conversation continues with what the source added) or `summary` (a caller-supplied message stands for the source). The engine never calls a model; a product that wants a model-written summary makes it first. A replay re-runs a branch's turns into a new, linear branch marked `replayOf`, optionally from a node of the branch and on another route.
- **SQLite through `node:sqlite`** (lead, 2026-10-12, M3). Node's built-in driver needs no native build, which keeps installs and cloud sessions simple. It requires Node 22.13 or later, and prints an `ExperimentalWarning` once per process (examples pass `--disable-warning=ExperimentalWarning`). Drizzle 0.45 has no `node:sqlite` driver and the store is one table, so it uses prepared statements directly.
- **The Postgres store takes any Drizzle database; tests use PGlite** (lead, 2026-10-12, M3). `drizzle-orm` is a peer dependency, so an app's single copy is used. The table `core_graph_events` ships as a Drizzle table for the app's own migrations, plus `ensureGraphSchema` for apps without them. `at` is text so timestamps come back exactly as written. Tests run on PGlite, which is Postgres compiled to WebAssembly and runs in the test process, so no server or network is needed.
- **A local CLI before the process graph** (owner, 2026-10-12, core#69). The owner wants to use core from the terminal now, signed in to the providers Trilix already uses. M2b ships `@core/credentials` and `@core/cli` before M3; it touches no M3 file.
- **Secrets live in the OS keychain, through `@napi-rs/keyring`, pinned to the Secret Service on Linux** (lead, 2026-10-12, core#69). The package ships prebuilt binaries (no native build), and `keytar` is archived. Spike: unpinned, it silently falls back to the Linux kernel keyring, which is lost on reboot; pinned, the constructor throws when no Secret Service runs. We then fall back to our own file, `credentials.json` in the config directory, mode `0600`, written atomically and refused when other users can read it. `CORE_CREDENTIAL_STORE` forces either store.
- **Environment variables win over saved sign-ins** (lead, 2026-10-12, core#69). CI and scripts keep working unchanged, and `core status` names the variable that is in effect.
- **Terminal sign-in reuses Trilix's flows** (lead, 2026-10-12, core#69). OpenRouter: PKCE with a localhost callback on any free port, issuing a key owned by the user's account. Cloudflare: authorization code with PKCE on Trilix's public OAuth client, with the fixed redirect `http://localhost:8976/oauth/callback` registered once by the owner; tokens are renewed before they expire. An API token plus account ID works without any OAuth setup. A new key is verified by listing models before it is saved.
- **Saved sign-ins are a contract** (lead, 2026-10-12, core#69). `StoredCredential` and `CredentialSummary` live in `@core/contracts` because the credentials package writes them and the CLI reads them; every record read back is validated.
- **Tab completion bakes the static words into the bash script** (lead, 2026-10-14, core#96). Starting `core` takes about 0.6 s, too slow for every Tab, so `core completion bash` writes the command names, options (read from each usage synopsis), providers and `config` keys into the script. Only a model route calls back into `core` (the hidden `core __complete route`), which completes `provider:` prefixes and asks the local Ollama for its models; it never lists remote providers or opens the keychain. The script reads `COMP_LINE`, because bash splits `COMP_WORDS` at `:`.
- **Sign in by link wherever a provider allows it** (owner, 2026-10-14, core#103). `core login cloudflare` uses the browser by default, with Trilix's public OAuth client ID built in (its terminal callback is registered); the environment and `cloudflare.oauth-client-id` still override it, and `--key` keeps the token flow. OpenAI, Groq and Vercel AI Gateway issue no key to a terminal app through a sign-in, so core opens their API-key page and asks for the key; it opens nothing when input is piped. `login`'s synopsis keeps `--browser`, because Tab completion reads options from it.
- **Claude through two providers, `anthropic` and `anthropic-aws`** (owner, 2026-10-15, core#120). The Claude API needs only a key, because each key already belongs to one workspace. Claude Platform on AWS also needs an AWS region (`https://aws-external-anthropic.{region}.api.aws/v1`) and a workspace ID, sent as `anthropic-workspace-id`; its keys come from the AWS Console, and Claude Console keys do not work there. Saved sign-ins therefore gain `region` and `workspaceId` (`accountId` keeps its meaning). The wire format goes through `@ai-sdk/anthropic`, always given an explicit base URL and key, so `ANTHROPIC_*` variables are never read. Claude models from 4.7 on reject `temperature`, so the adapter drops it for them. Deferred: SigV4 and short-term AWS keys (core#130), thinking blocks in assistant messages (core#131), prompt caching, effort and refusal handling (core#132).
- **Structured output is a JSON Schema on the request, validated by core** (lead, 2026-10-15, core#110). `ChatRequest.outputSchema` is a JSON Schema record, `ChatResponse.output` is the parsed value, and `ModelCapabilities.structuredOutput` says whether a provider takes it. `outputSchemaFrom(zodSchema)` builds the record; `parseStructuredOutput` strips a code fence, parses and validates, so every provider accepts and rejects the same text. A bad reply is `unknown`, an unsupported request is `bad_request` (no new error code). The OpenAI-compatible provider sends the schema to the endpoint only when the request carries one. The router skips routes without `structuredOutput` and fails `bad_request` when none qualifies. Streaming rejects an `outputSchema` for now (follow-up core#133).
- **`core ask` serves programs too** (lead, 2026-10-15, core#135). A caller such as HiQ's import runs `core ask` as a subprocess and uses the saved sign-ins. `--schema <file>` sends `outputSchema`, and `--json` prints one `AskResult` (`@core/contracts`: the model, text, output, usage and the router's attempt log, or the error and the attempts). Either option takes `router.chat`, without streaming or tools; without them `ask` streams through `runTurn` as before. `--system-file <file>` is named for the file, because `core chat --system` takes text. `--timeout <ms>` sets the per-step timeout for one call, so a caller doesn't rewrite the user's saved config; in `chat` it bounds the whole call. With `--json`, every failure after the arguments parse still prints a result, including usage errors (`bad_request`, exit 2). The exit codes and stderr lines are unchanged. The router's attempt entry moved into contracts as `RouteAttempt`.
- **`core ask --max-output-tokens` limits each model request; a cut-off structured answer says so** (lead, 2026-10-15, core#144). Some providers stop a reply early when no limit is sent (Cloudflare stopped `gpt-oss-120b` at 256 tokens, all spent on reasoning), and core then reported "not valid JSON". The option sets `ChatRequest.maxOutputTokens` on every step of the route, and `runTurn`'s per-request `maxOutputTokens` on the streamed path; it never sets `TurnBudget.maxOutputTokens`, which caps a whole turn. Without it nothing is sent, as before. When a request with `outputSchema` finishes with `length` and the text does not parse or match, `parseStructuredOutput` throws `unknown` with a cut-off message and `details.finishReason: "length"` (no new error code; programs read it from `attempts[].error.details`). Text that still validates is returned. No default limit and no config key for now.
- **Two cores, one API** (owner, 2026-10-17, core#20). Trilix's website talks to two cores through one HTTP API: the one mounted in Trilix's Next.js app (hosted features, signed-out use) and `core serve` on the user's machine (local models, saved sign-ins). The browser picks the address, and the server code is the same. The local path needs the browser on the machine that runs `core serve`. Chromium browsers ask once for local-network access, and Safari blocks `http://127.0.0.1` from https pages (WebKit bug 279249), so Safari users get the hosted core only. A tunnel from the local core to the hosted one (phones, Safari, server-side jobs) is deferred.
- **M4 splits in three** (lead, 2026-10-17, core#20). core#20 ships what Trilix needs: `@core/server`, the local bridge, `@core/client` and packs for consumers. The MCP endpoint with server-side tools (core#152) and the generated Python client for Orbit (core#153) are their own parents in M4.
- **A web-standard handler on Hono** (lead, 2026-10-17, core#20). `createCoreHandler(options)` returns `{ fetch(request) }`. A Next.js catch-all route calls it unchanged, and `core serve` runs it on 127.0.0.1 through `@hono/node-server`, from the `@core/server/node` subpath so browsers and Next.js never import it. Hono has no dependencies and gives routing, SSE and body limits; nothing Hono-typed is in the public API. The OpenAPI 3.1 document is assembled from `toJsonSchemas()`, with no second schema library. Errors map to HTTP statuses by code (`bad_request` 400 … `timeout` 504), and POST bodies must be `application/json`.
- **Tenancy belongs to the host app** (lead, 2026-10-17, core#20). The handler takes `authenticate(request) → Principal | null`, `credentialsFor(principal, request)` and, for graph routes, a `GraphAccess` (read, write, created, list). Core's graph keeps no owner, and a graph the principal may not read answers the same 404 as a missing one. Providers are built per request from the presets (`createPresetRegistry`), because a provider binds its credential store when it is made. `POST /v1/chat` answers the same `AskResult` as `core ask --json`, built by one function (`askResultFrom`).
- **Client tools end the turn** (lead, 2026-10-17, core#20). Trilix runs a model's tool calls in the browser after the user clicks. `RunTurnOptions.clientTools` declares tools the runtime offers but never runs. A round that calls one runs the registry's own calls of that round, then ends the turn with `client-tools`; the caller runs them and continues with the tool messages. Turns over HTTP in core#20 have an empty registry, and server-side tools come with core#152.
- **The local bridge** (lead, 2026-10-17, core#20). `core serve` binds 127.0.0.1 only (default port 8977), and the `Host` header must be `127.0.0.1:<port>` or `localhost:<port>`, against DNS rebinding. Only paired origins get CORS, with `Access-Control-Allow-Private-Network` on preflights that ask for it; any other origin may only ask to pair. A site pairs by showing the user a six-character code. The terminal running `core serve` prints the origin and the same code and asks y/N, and without a terminal pairing is refused. One request pends at a time, and a denied origin waits 60 s. The site gets a bearer token bound to its origin. Only its SHA-256 is stored, in core's secret store: the name is `serve-token-` plus the first 32 hex characters of the origin's SHA-256, because secret names allow only lowercase letters, digits and hyphens, and the value is JSON `{ origin, hash }`. A presented token's hash is compared in constant time. Programs on the machine use the token in `<configDir>/serve-token` (mode `0600`). Requests from sites run on channel `web`, programs on `local`. `core unpair <origin>` and `DELETE /v1/pair` revoke. There are no cookies.
- **The TypeScript client is written over the contracts, not generated** (lead, 2026-10-17, core#20). `@core/client` imports only `@core/contracts` and checks every answer and stream event with its schema, so it runs in browsers and its types come from the one definition. The Python client is still generated, from the OpenAPI document.
- **Packed tarballs until the name is decided** (lead, 2026-10-17, core#20, core#24). Nothing is published while the name is open. `pnpm pack:consumers` packs the packages a consumer imports into `packs/`, with a manifest of names, versions and SHA-256s. Trilix vendors a pinned set and installs it with `file:` dependencies plus npm `overrides`.
- **M5 splits by repository** (lead, 2026-10-17, core#21). core#154 adds the providers Trilix uses that core lacks (any OpenAI-compatible endpoint, Google Gemini, Azure OpenAI). GitHub Models is not ported: GitHub retired it on 2026-07-30. core#155 moves Trilix's chats onto core, in the trilix repo. core#156 moves Trilix's graph onto the event log; it is shaped after core#155, because Trilix's canvas (node kinds, positions, group memory) has no counterpart in core's graph yet. AWS Bedrock is not ported: Trilix's Bedrock path posts to a proxy that never existed. The free trial stays on its own route for now. Ollama keeps a direct browser path for users who don't run `core serve`. Signed-out chats run on the hosted core as the browser session. Provider requests from Trilix's server go through an SSRF guard (no loopback, private, link-local or metadata addresses, checked at connect time), because users can supply base URLs. Whether the browser sends keys to Trilix's server with each chat was the owner's call; see the next entry (core#157).
- **Keys go per request, or never leave the machine** (owner, 2026-10-17, core#157). In the hosted mode, the browser sends a chat's key to Trilix's server with each request. The server holds it in memory for that request only and never stores or logs it, and a test checks this. A user who wants keys never to leave their computer turns on the local bridge for every provider: chats then run on that machine with core's own sign-ins, and never fall back to the hosted core. The browser stops calling keyed providers directly. Keeping keys in localStorage proved only that the server stores nothing, since the site's own script can read them, and it cost Trilix a second model stack.
- **Images are parts of a user message** (lead, 2026-10-19, core#213; in M5 by the owner's decision). A user message's `content` is a string, or a list of text and image parts. An image is an http(s) URL or `data:image/<type>;base64,<data>`, and nothing else. System, assistant and tool messages stay text. `messageText()` gives a user message's text to whatever reads it as text, such as the mock provider and the branching-chat example. The models layer hands images to the AI SDK as `file` parts with their media type. Which providers get images is the client's choice; a model that can't take them fails with the provider's own error.
- **An injected `fetch` also downloads images, and its guard must check every connection** (lead, 2026-10-19, core#217). When a model can't fetch an image link itself, core sends it the bytes. With a `fetch` passed in (`ProviderOptions.fetch`, or the handler's `fetch`), core downloads through it: a GET with a 30 s timeout and a 10 MiB cap, `image/*` only, with errors that name only the host. Without one (`core serve`, the CLI), the AI SDK's own downloader stays, with its own address checks. Core lets that `fetch` follow redirects and doesn't check addresses itself. So a host that guards addresses must check every connection, redirects included, as Trilix's guard does when it connects. Provider calls already need that, because in hosted use their base URL can come from the visitor. There is no limit yet on one call's downloads taken together (core#223).
